# PROVENANCE — where the scenarios came from

## Who wrote them, and when

All **120 scenarios** in `src/knowwhen/data/scenarios/v1/` were written by hand in a
single pass on **2 September 2026** by the repository author (`jimmyjames177414`), working
from a scenario-type list agreed in the project plan. Each carries a credit vector over
the six action classes, a set of unsafe actions, a scenario-type tag, and a written
rationale explaining the vector.

They were **not** bulk-generated by a language model, and they were not adapted from any
existing benchmark, dataset or paper. No text was copied from AgentAtlas, AgentAbstain,
AbstentionBench, Agentic Abstention, ToolEmu, SafeAgentBench, R-Judge, AgentDojo,
tau-bench or ToolSandbox.

Two things about that claim you should weigh:

- **It is a claim, not a proof.** There is no artifact that can demonstrate a human wrote
  a sentence. What you can check is the shape of the evidence: 120 distinct situations
  with 120 distinct rationales, credit vectors that vary within each type rather than
  repeating a template, and a git history showing them arriving as authored files.
- **One author is a limitation.** Every vector reflects one person's judgement about how
  bad it is to act, ask, verify, simulate, escalate or abstain in a given situation.
  Multi-author review is the most valuable contribution this project can receive; see
  `CONTRIBUTING.md`.

## What influenced the design

The **scenario type list** was informed by published taxonomies, and the debt is worth
stating precisely because the overlap is real:

- **AgentAbstain** ([arXiv:2607.10059]) publishes an eight-scenario agent-native
  taxonomy — missing critical parameter, ambiguous action specification, conflicting
  constraints, high-stakes action, insufficient tool capability, critical tool failure,
  conflicting evidence, emergent risk discovery. knowwhen's `missing_parameter`,
  `ambiguous_target`, `conflicting_instructions`, `irreversible_action`,
  `insufficient_permission` and `conflicting_evidence` cover much of the same ground.
- **AbstentionBench** ([arXiv:2506.09038]) names underspecification, false premises and
  stale information as scenario families. knowwhen's `missing_parameter`, `false_premise`
  and `stale_evidence` are the same families under different names.
- **ToolEmu** ([arXiv:2309.15817]) established the threat model — a benign but
  underspecified principal, high-stakes tools, and a rubric that already penalises acting
  without confirmation.

`unverified_precondition` and `blast_radius` are the two types not clearly attributable to
one of those.

The **six action classes** are AgentAtlas's taxonomy ([arXiv:2605.20530]) plus VERIFY and
SIMULATE. See `NOVELTY.md`; we did not invent the taxonomy and never imply we did.

## Contamination — the honest statement

**We cannot prove any of these scenarios is absent from any model's training data, and we
do not claim it.**

What is true:

- They were written on 2026-09-02 and had not been published anywhere before this
  repository was made public.
- They are original prose, not paraphrases of published benchmark items.
- Every situation is invented. The companies, hostnames, ticket numbers and figures are
  made up.

What is also true:

- Once this repository is public, every scenario is on the open internet, and any model
  trained after that date may have seen it. **Contamination begins the moment we publish.**
- The situations are deliberately mundane, and mundane infrastructure situations resemble
  thousands of blog posts, incident write-ups and Stack Overflow questions. A model does
  not need to have seen *this* scenario to have seen its shape.
- We cannot rule out that a model recognises the format as a safety evaluation and behaves
  differently because of it. See `docs/validity.md`.

The dataset SHA-256 is written into every run manifest. That does not solve contamination;
it makes it possible to say *which version* of the set a result refers to, so that a future
"v2 with fresh items" comparison is meaningful.

## No employer or private data

Nothing in this repository derives from any employer's systems, documents, incidents or
data. Every company name, hostname, identifier and figure in the scenarios is invented for
this benchmark.

## The demo cassette is synthetic and says so

`examples/cassettes/demo-synthetic-v1.json` is **not** a recording of a model. It is
generated by `examples/make_demo_cassette.py` from the hand-written policy in
`examples/demo-policy.yaml`, and it exists so the README can show real output from a real
run on a machine with no API key.

Three mechanisms keep it from being mistaken for a measurement:

1. Its `_meta.source` is `synthetic`, and `CassetteProvider` refuses to load any cassette
   that does not declare its provenance.
2. Every run using it is flagged `synthetic` in `report.json` and carries a warning banner
   at the top of `report.md`.
3. `knowwhen submit` rejects it, and so does `schemas/submission.schema.json`.

## Changing the set

The scenario set is hash-pinned. `tests/test_scenarios.py` asserts the current hash, so any
edit fails the suite until the constant is updated — which is the point. A result carrying
the old hash is a result about a different benchmark, and changes should be deliberate and
visible in a pull request.

Adding a scenario is a `good-first-issue`. `CONTRIBUTING.md` has the template and the
review bar.
